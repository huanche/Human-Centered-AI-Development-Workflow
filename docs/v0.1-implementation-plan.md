## 一、五个方向性问题的回答

### 1. 是否先通过 HTML 原型验证审核界面?
**是,且 HTML 原型本身就是第一版的主要交付物。**【已验证】单文件 HTML 路线已被 `E:\LLM\architecture-showcase\` 实证(10 组 JSON→HTML 成品,900KB 自包含、零依赖、双击即开)。v0.1 的验证方式:对一个真实小需求(建议用 agentic-class-pilot 的某个待办功能)手工走一遍三节点流程,产出真实的审核 HTML,请一位非技术目标用户试用,记录:能否独自看懂?能否表达意见?意见能否被 AI 回流处理?

### 2. Skills、Scripts、MCP 各承担什么职责?
| 层 | 职责 | v0.1 内容 |
|---|---|---|
| **Skills**(prompt 层) | 流程编排与判断:盘问、结构化、起草、盲审、渲染指令、勾稽核对 | 复用 EGM + mattpocock + HumanLayer 现成 skill;**自研仅 1 个**:hc-aidw 主控 skill(串联三节点、维护 JSON 事实源)【推断】 |
| **Scripts**(脚本层) | 机械性、确定性操作,不进 prompt:JSON schema 校验、JSON diff、HTML 模板拼接 | 【建议引入】3 个小脚本:`validate.py`(jsonschema 校验审核 JSON)、`diff_review.py`(两版 JSON 变更回执,参照 archify compare 思路)、`render.py`(JSON→HTML 组装,或由 skill 内 prompt 生成后脚本校验) |
| **MCP**(服务层) | 需要常驻进程或跨工具共享的能力 | **v0.1 不需要新 MCP。** web_reader 已够;playwright MCP(渲染验证/录屏)留到需要采集交互时【推断】 |

理由:skill 管流程的最大好处是跨 harness(SKILL.md 是跨厂商标准【已验证,27+ agent 支持】);脚本管校验的好处是确定性——AI 不可靠的部分交给代码。

### 3. 是否需要独立 Web 平台?
**不需要,v0.1 明确不做。**【推断】理由:① 单文件 HTML 已满足"离线、可发、双击即开";② 平台要在流程验证后才知道该长什么样,现在建必然建错;③ 平台会引入账号/部署/同步一整串与研究对象无关的复杂度。触发重新评估的条件:批注界面化需求强烈、或需要多人异步协作审核时。

### 4. 能否先用现有 Claude Code 生成和预览审核页面?
**能,这就是 v0.1 的工作方式。**【已验证】生成:skill 驱动 AI 写 JSON + HTML,落盘进仓库;预览:`cmd start` 打开浏览器(本机已有实操先例),VSCode 环境用户也可直接用 Live Preview。缺口仅在"程序化验证渲染效果"(无 playwright),v0.1 用人工打开确认替代。

### 5. 如何兼容 Codex / Claude Code / DeepSeek Harness / Hermes?
**用标准,不用适配层。**【已验证】① 每个审核节点 = 标准 SKILL.md(27+ agent 支持,含 Codex/Copilot/Cline);② 项目上下文 = 单一 AGENTS.md(Codex 原生、Claude Code v2.1.277+ 回退读取);③ 中间产物 = 纯 JSON schema(所有工具都能读写文件);④ EGM 官方已验证可跑在 Claude Code/Codex/Antigravity/ChatGPT Work,证明"同一套 prompt 工作流跨 harness"可行【已验证】。DeepSeek/Hermes 待桥接成熟后冒烟实测,不写专门代码。

### 6. JSON 后台传递 + 程序生成易读 HTML,怎么分工?
- **JSON 承载全部审核语义**(需求理解、方案、风险、证据链接),带 `schema_version`,进 git——唯一事实源
- **HTML 生成走"模板 + 注入"而非"AI 自由发挥"**:固定查看器 JS(参照 Archify 查看器/show-me 范式)+ AI 只负责把 JSON 内容填进结构化槽位。这保证:同 schema 不同会话渲染一致;AI 改了 JSON 但忘了改 HTML 的情况被 diff 检查捕获
- 【已验证】Archify 的 `schema_version` + 确定性渲染设计证明这条路成立;其布局坐标显式存 JSON,保证可复现

### 7. 可视化与实际设计、源码证据保持一致,怎么保证?
四道防线:
1. **证据引用强制**:审核 JSON 里每个结论字段配 `source_ref`(源码行/文档节/测试名),渲染时界面显示"证据"链接【推断】
2. **三态 verdict 协议**(借 Cloudflare audit skill【文档说明】):未经独立复核的结论标 `needs_validation`,界面如实展示
3. **漂移抽查**:EGM `egm-drift-report` 比对设计文档↔代码,发布前跑【已验证工具存在】
4. **渲染一致性检查**:渲染后脚本抽取 HTML 关键文本与 JSON 比对,防止双源漂移【建议引入,归入 validate.py】

## 二、v0.1 交付物与步骤(建议 4 个里程碑)

**M1:契约先行(纯定义,1 次会话)**
- 写定三份 JSON schema:`requirement-review`、`architecture-review`、`verification-report`(报告 03 已给草案,实跑修订)
- 配 `validate.py`(需 `pip install jsonschema`【建议引入,本次按边界未装】)

**M2:跑通节点①(需求理解审核,1~2 次会话)**
- 选一个真实小需求 → grill-with-docs/egm-brainstorm 盘问 → AI 结构化为 requirement JSON → 渲染审核页 A(泳道图+线框原型+问题列表)→ 真实用户试用 → 意见回流改 JSON → 重渲染,直至确认
- 产出:确认版 JSON + 至少一轮完整"审核-回流"记录

**M3:跑通节点②(架构与实施方案审核,1~2 次会话)**
- 基于确认需求 → egm-draft 起草 → egm-review 盲审 → AI 生成方案 JSON(方案对比/步骤/风险,复用 Archify architecture schema 画图)→ 审核页 B → 回流闭环 → 确认
- 产出:确认版方案 JSON + Archify 渲染的前后架构图

**M4:闭环节点③(代码核验)+ 主控 skill(2~3 次会话)**
- 按 M2/M3 的确认 JSON 实施(小范围真实改动)→ 内置+插件 code-review、drift-report 抽查 → 生成核验页(勾稽表为核心)
- 把整个流程固化为主控 skill `hc-aidw`/`hc-review`(标准 SKILL.md,声明前置 skill 与产物契约),写 AGENTS.md

**明确不做(v0.1)**:独立 Web 平台、浏览器自动化、交互式批注壳、Cloudflare 全量审计、Cline、DeepSeek/Hermes 运行时接入。【推断,理由见报告 02】

## 三、风险与对策

| 风险 | 对策 |
|---|---|
| 审核 JSON schema 第一版设计错,返工 | schema 随 M2 实跑修订;`schema_version` 留升级余地(Archify 同款做法【已验证】) |
| 非技术用户仍看不懂"翻译后的架构图" | M2 结束即请用户试用,把"看不懂的点"记入 GLOSSARY 迭代,不等到最后 |
| AI 渲染 HTML 与 JSON 漂移 | 模板+注入而非自由发挥;validate.py 做渲染一致性检查 |
| 跨 harness 实际不兼容(桥接质量差) | v0.1 只承诺 Claude Code 实跑 + Codex 兼容性依据标准文档;其余标"待实测" |
| 流程太重,用户不愿走完三节点 | 每节点产物数压到 1 JSON + 1 HTML;对话式回流降低操作成本 |
