# HC-AIDW 报告 03:第一版可视化审核界面设计方案

> 调查日期:2026-11-06
> 目标:让**非技术人员**审核 AI 的①需求理解、②架构与实施方案,并基本核验③代码结果。原则:用户不读 Markdown/JSON 原文,但所有界面内容必须能追溯到 JSON 证据,JSON 能追溯到源码/文档。
> 标注约定同前。【已验证】【文档说明】【推断】【建议引入】

## 一、总体架构:一条铁律

**JSON 是唯一事实源,HTML 只是投影视图。**

```
需求/方案讨论(对话)
   ↓ AI 结构化
review-requirement.json / review-architecture.json   ← 唯一事实源(进 git)
   ↓ 渲染器(Archify 模式)
单文件 HTML(自包含、零依赖、可离线发给任何人)     ← 只读投影
   ↓ 用户在界面/对话中表达意见
feedback(结构化为 JSON patch 或自然语言)           ← 意见回流
   ↓ AI 读取
修改 JSON → 重新渲染 → 再次评审 …(循环至用户确认)
   ↓ 确认后的 JSON
驱动实现 → 代码核验节点用同一份 JSON 做符合性比对
```

【已验证】这条链路每一环都有现成参照:
- JSON schema + 单文件 HTML 渲染:Archify 已在本地产出过 10 组成品(`E:\LLM\architecture-showcase\`)
- 意见结构化回流:Archify `archify compare` 可输出两版 JSON 的评审变更回执;mattpocock `to-questionnaire` 可把待确认问题变成问卷
- "渲染内容与源码一致"的守门:EGM `egm-drift-report` 的文档↔代码比对机制

【推断】为什么必须坚持这条铁律:如果 HTML 手写(不经 JSON),界面好看但无法回写、无法比对、无法追溯,审核就退化成"看 PPT"。JSON 中间层是 HC-AIDW 与"演示文稿"的本质区别。

## 二、界面 A:需求理解审核

### 2.1 要展示什么 → 用什么形式

| 内容 | 形式 | 交互 | 为什么这个形式 |
|---|---|---|---|
| AI 对需求的理解(一句话重述) | 页首高亮卡片 | 无 | 用户最先核对"AI 是不是懂我"——一句人话,不是术语 |
| 用户角色与使用场景 | 角色卡片(头像+一句话+典型一天时间线) | 点击展开该角色的完整旅程 | 非技术用户对"角色/场景"有直觉;时间线比文字段落易核对 |
| 业务流程 | 垂直泳道图(每角色一条泳道,步骤卡片) | 点击步骤 → 右侧详情(输入/输出/异常分支/对应原文引用) | 泳道图是业务人员最熟悉的流程表达;点击展开避免一次塞满 |
| 交互式原型 | 低保真 HTML 线框(可点击翻页,不接真数据) | 点按钮、填假表单,走通主流程 | **这是需求审核的灵魂**:用户"用"一遍 AI 理解的产品,误解立刻暴露——比读十段文字有效 |
| 预期效果 | 前后对比滑块(现状 vs 改造后示意) | 拖动对比 | 对"效果"的期待差异是需求分歧的主因,对比最直观 |
| 待确认问题 | 右侧问题列表(每条:背景+选项按钮) | 点选答案/填自定义 → 即时写入 feedback 区 | 把"盘问"从对话里搬到界面上,用户批量作答(mattpocock to-questionnaire 同思路) |
| 用户修改意见 | 每个元素可"标记有疑问"→ 弹评论框 | 评论落到 JSON 对应节点 | 意见必须锚定到具体元素,否则 AI 无法精确回流 |

### 2.2 数据契约(建议的 JSON 顶层结构)

```jsonc
{
  "schema_version": 1,
  "type": "requirement-review",
  "status": "draft | under-review | confirmed",
  "restatement": "AI 对需求的一句话理解",
  "actors": [{ "id": "teacher", "name": "教师", "pain_points": [], "journey": [] }],
  "flows": [{ "id": "publish", "steps": [{ "id": "s1", "actor": "teacher",
              "action": "", "input": "", "output": "", "exceptions": [], "source_ref": "" }] }],
  "prototype": { "screens": [{ "id": "", "elements": [], "links": [] }] },
  "open_questions": [{ "id": "q1", "question": "", "options": [], "answer": null }],
  "feedback": [{ "target": "s1", "comment": "", "resolved": false }]
}
```

每个 `source_ref` 指向用户原话/文档出处——满足"可视化与证据一致"。【推断,结构待 v0.1 实跑修订】

### 2.3 现有能力落位

- 生成 `restatement/actors/flows/open_questions`:mattpocock `grill-with-docs` 或 EGM `egm-brainstorm` 的产出直接结构化
- 原型线框:【建议引入】第一版由 AI 按固定模板生成(卡片+按钮的 HTML 骨架,不追求美观追求走通流程);视觉规范采用 HumanLayer `show-me` 的生成范式【已验证 SKILL.md】:贴宿主产品设计 token、**必须用真实数据不用占位假数据**、diagram/infographic/slide deck 三态产物、单文件输出——"真实数据"这一条尤其重要,审核界面里的示例数据若为 AI 编造,会污染用户对需求的理解
- 渲染与交互壳:参照 Archify 查看器(自研 JS、单文件、点击展开/详情面板模式)【已验证可行】

## 三、界面 B:架构与实施方案审核

### 3.1 要展示什么 → 用什么形式

| 内容 | 形式 | 交互 |
|---|---|---|
| 现有架构 vs 改造后架构 | **双栏切换**(同一布局语言画两版)+ 高亮 diff(新增绿/删除红/修改琥珀) | 切换开关、并排模式;点"只看变化"过滤未变模块 |
| 模块职责 | 点击模块 → 侧滑详情:一句话职责、输入/输出、对外契约、源码证据链接 | 层级展开:系统 → 模块 → 文件 |
| 模块间调用关系 | Archify architecture 图(节点+连线) | 点模块 → 高亮其上下游可达链路(Archify 原生支持【已验证】) |
| 数据流 | Archify dataflow 图(sequence 图) | 路线追踪:从"一次用户操作"出发看数据走全程【已验证 Archify sequence 支持路线追踪】 |
| 方案对比 | 方案卡片(A/B/C)并排,每卡:示意图+3 条优点+3 条代价 | 选卡对比、展开证据("为什么这么说"→链接到基准测试/文档/代码) |
| 推荐理由 | 推荐卡置顶 + "为什么不是另一个方案"折叠区 | 点击展开被否方案的否决原因 |
| 实施步骤 | 垂直时间线(每步:改哪些模块+验收标准) | 步骤打钩跟踪,点步骤看涉及文件清单 |
| 风险和证据 | 风险表(风险/概率/影响/缓解/证据链接),用【已验证】三态标记(确认/待验证/已排除) | 点证据看原始出处 |

### 3.2 面向非技术人员的三条翻译原则

1. **每个技术概念旁边站一个人话版本**:模块→"负责什么差事";依赖→"谁得先做完才行";数据流→"数据从哪来、到哪去"。界面层维护 `term → plain` 映射表(可复用 grill-with-docs 产出的 GLOSSARY.md)。【推断】
2. **默认视图只回答三个问题**:现在是什么样?要改成什么样?为什么要改?——其余全部折叠进"详情"。
3. **任何结论必须带"我怎么知道的"**:点击理由/风险/数字 → 展示证据(源码行、测试结果、文档引用)。没有证据的结论标"待验证"。这是对 AI 幻觉的界面级防线,配合 EGM drift-report 抽查。

### 3.3 数据契约(建议顶层)

```jsonc
{
  "schema_version": 1,
  "type": "architecture-review",
  "status": "draft | under-review | confirmed",
  "current": { "arch_ref": "archify-json 或其引用" },
  "proposed": { "arch_ref": "", "diff_highlights": [] },
  "options": [{ "id": "A", "summary": "", "pros": [], "cons": [], "evidence": [], "rejected_because": null }],
  "recommended": "A",
  "steps": [{ "id": "", "modules": [], "acceptance": "", "files_touched": [] }],
  "risks": [{ "desc": "", "verdict": "confirmed|needs_validation|refuted", "evidence": [], "mitigation": "" }],
  "feedback": [{ "target": "", "comment": "", "resolved": false }]
}
```

`arch_ref` 直接引用 Archify 的 architecture/dataflow JSON——**架构图不另造 schema**,复用已验证的格式。【推断】

## 四、界面 C:代码结果核验(基本形式)

第一版只做一页"核验报告"式静态页:

| 内容 | 形式 |
|---|---|
| 实际功能效果 | 三段式:① 短视频/GIF 式操作录屏(人工录,或第二阶段 playwright 自动录);② 测试结果摘要(通过/失败计数,失败可展开看日志);③ `run` skill 的启动与验证记录 |
| 需求与实现对应关系 | 双栏对照表:左列=已确认 JSON 里的每条需求/流程步骤,右列=实现位置(文件+函数链接)+ 状态(已实现/部分/未实现)。**数据直接来自确认版 requirement JSON,逐条勾稽** |
| 代码变更摘要 | 按模块分组的 diff 统计 + 每模块一句话"改了什么、为什么"(引用方案 JSON 里的步骤) |
| 测试结果 | 通过率、新增测试列表、失败详情折叠 |
| 未解决问题 | 遗留项清单(每条:是什么/为什么不现在修/跟进方式) |

【推断】核验页的关键设计:**勾稽表**——确认版 JSON 的每一条都必须在右列有着落,反过来实现里多出来的东西也要列出("实现超出已确认范围"清单)。这样"代码是否符合需求"从感觉题变成对账题。

核验引擎复用:内置 `code-review`(bug)+ 插件版 `code-review`(规范+spec 符合)+ EGM `egm-drift-report`(文档↔代码漂移)+ Cloudflare 式三态 verdict 协议(结论必须 confirmed/needs_validation/refuted 且附证据)。【已验证工具存在;组合方式为推断】

## 五、交互实现的技术选型

| 方案 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| **自包含单文件 HTML(Archify 模式)** | 零依赖、离线可发、进 git、用户双击即开 | 交互壳要自研(但 Archify 查看器 JS 可参照/复用) | ✅ 第一版主线 |
| 轻量审核壳(本地起个静态服务,HTML+少量 fetch) | 可保存批注到本地文件 | 要装依赖、要起服务,用户多一步 | ⏸ 第二阶段,批注需求强烈时再上 |
| 独立 Web 平台 | 功能不受限 | 违背"不过早建复杂系统" | ❌ 不做 |

【已验证】单文件路线已被 architecture-showcase 实证走通(900KB 含全部交互)。【推断】批注回写是单文件模式的短板:第一版用"对话式回流"绕开——用户在聊天里说"A 方案的并发估算我不信"或点界面上的"复制问题编号",AI 负责把话变成 JSON patch。零开发成本,先验证流程,再决定要不要交互式批注壳。

## 六、待用户决策的分歧点

**分歧 1:需求审核界面里,交互式原型做多重?**
- 选项 a:低保真线框(固定模板,不接数据)——便宜,足以暴露流程误解
- 选项 b:高保真可点原型(接近真实 UI)——说服力强,但每轮生成成本高、用户容易把"原型好看"误认为"实现快好了"
- **推荐 a**,理由:第一版目标是验证"审核流程"而非"原型工具";且高保真原型的"看起来做完了"效应对审核反而有害【推断】

**分歧 2:架构 JSON 是否完全采用 Archify schema?**
- 选项 a:完全复用 Archify 的 architecture/dataflow/erd schema,方案对比、风险等审核特有信息放外层信封 JSON 引用它
- 选项 b:为审核场景自定义 schema,Archify 仅作渲染后端
- **推荐 a**:schema 已验证、渲染器现成、生态一致(10 种图型够用);自定义 schema 省不了多少事还丢了 compare 等工具链【推断】

**分歧 3:批注回流第一版走对话还是做界面批注?**
- **推荐对话**(见第五节),界面批注留第二阶段。若用户强烈倾向界面批注,则第五节方案改为"审核壳+本地批注文件",工作量约多一个 star 级前端原型。【推断】
